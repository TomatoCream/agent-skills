# Generating org-anki Flashcards: The Multiline Basic Standard

This skill defines the standardized format and generation workflow for creating Org-mode flashcard documents compatible with the `org-anki` Emacs package.

All flashcards generated by this skill follow a single, robust architecture: **The Multiline Basic Front & Back Subheading Pattern**.

---

## 1. The Standard Card Architecture

Every card is authored using explicit level-3 child headings for `Front` and `Back`, tagged `:noexport:`:

```org
** Concept Name or Descriptive Title :anki:tags:
:PROPERTIES:
:ANKI_NOTE_TYPE: Basic
:END:
# Optional in-buffer study notes or source references go here.
# org-anki ignores text above *** Front because both fields are
# supplied by child subheadings below.

*** Front :noexport:
Concise question, problem statement, code block, or mathematical prompt.

*** Back :noexport:
Direct answer, explanation, proof, or key architectural takeaway.
```

### Why This Style Is Mandatory
1. **Multi-Line & Rich Syntax Support:** The `Front` can hold syntax-highlighted code blocks (`#+BEGIN_SRC`), LaTeX equation environments (`\begin{equation}` / `\begin{align}`), Org tables, and multi-paragraph prompts without escaping issues.
2. **Buffer Note Isolation:** Any text placed between `:END:` and `*** Front :noexport:` serves as personal notes or citations in the Org buffer and is **never** pushed to the flashcard.
3. **No Stub Cards (Subheading Isolation):** With `org-anki-inherit-tags t`, child subheadings inherit parent tags. The `:noexport:` tag on `*** Front` and `*** Back` instructs `org-anki-sync-all` (`+anki-noexport`) to skip them during buffer mapping, while `org-anki--get-fields` scans them via direct child inspection.
4. **Clean Note ID Lifecycle:** Omission of `:ANKI_NOTE_ID:` allows `org-anki` to invoke `addNote` on first sync, automatically stamping the returned ID into `:PROPERTIES:`.

## 2. Standard File Template

When generating a new flashcard deck, use this exact skeleton:

```org
#+TITLE: <Deck Title>
#+AUTHOR: <Author / Topic>
#+STARTUP: overview showeverything
# ---------------------------------------------------------------------------
# BUFFER-WIDE SETTINGS (org-anki Precedence Tier 3)
# ---------------------------------------------------------------------------
#+ANKI_DECK: <Target Deck Name>
#+ANKI_NOTE_TYPE: Basic
#+ANKI_MATCH: anki-noexport
#+ANKI_TAGS: <global_tag_1> <global_tag_2>

* <Category 1 Name> :anki:<category_tag>:

** <Card 1 Title> :<topic_tag>:
:PROPERTIES:
:ANKI_NOTE_TYPE: Basic
:END:

*** Front :noexport:
<Front content>

*** Back :noexport:
<Back content>

** <Card 2 Title> :<topic_tag>:
:PROPERTIES:
:ANKI_NOTE_TYPE: Basic
:END:

*** Front :noexport:
<Front content>

*** Back :noexport:
<Back content>
```

## 3. The 6 Strict Generation Rules

1. **Only Basic Note Types:**
   - Always set `:ANKI_NOTE_TYPE: Basic` in the card's `:PROPERTIES:` drawer.
   - Do **not** use Cloze, Reversible, or custom note models unless explicitly instructed.

2. **NEVER Output `:ANKI_NOTE_ID:`:**
   - Generated cards must never include `:ANKI_NOTE_ID:`.
   - Let `org-anki` stamp the real integer ID returned by AnkiConnect upon first synchronization.

3. **Always Tag Field Subheadings `:noexport:`:**
   - Child headings must be verbatim: `*** Front :noexport:` and `*** Back :noexport:`.
   - Failure to add `:noexport:` causes `sync-all` to treat `Front` and `Back` as separate flashcards.

4. **Category Headings Must Be Bodyless:**
   - Level-1 headings (`* Category Name :anki:topic:`) must have **no direct body text** under them before the first card heading (`** Card Title`).
   - If category-level documentation is needed, wrap it in a child heading tagged `:noexport:`:
     ```org
     * Operating Systems :anki:os:

     ** Category Overview & References :noexport:
     Study notes and documentation here will not become flashcards.

     ** Actual Flashcard Title
     ...
     ```

5. **Atomicity & Card Quality:**
   - **One Question, One Answer:** Each card tests exactly one concept, edge case, formula, or mechanism.
   - **Direct Answer First:** The `Back` field must state the direct answer in the first sentence or bullet, followed by the concise explanation or proof.
   - **Context Independence:** The card must be answerable on its own without assuming prior cards were seen.

6. **Syntax & Formatting Standards:**
   - **Math:** Use `$inline$` for short expressions and `\begin{equation} ... \end{equation}` or `\begin{align} ... \end{align}` for multiline equations (`org-anki` converts them to Anki MathJax `\[ ... \]`).
   - **Code:** Use `#+BEGIN_SRC <lang>` ... `#+END_SRC`. Keep code snippets under 15 lines, highlighting only the relevant logic.
   - **Tags:** Use `lower_snake_case`. Use double underscores `__` for hierarchical sub-tags (`systems__concurrency` $\to$ `systems::concurrency` in Anki).

## 4. Worked Card Recipes

### Recipe A: Comprehensive Masterclass Card (Code, Math, Tables, Media)
```org
** Virtual Memory Page Table Descriptors :mmu:kernel:
:PROPERTIES:
:ANKI_NOTE_TYPE: Basic
:END:
# Architectural study notes:
# - x86-64 4-level paging descriptor format
# - Page fault exception vector 14 (#PF)

*** Front :noexport:
In concurrent operating system kernel architectures, analyze the following virtual memory page table descriptor layout:

#+BEGIN_SRC c
/* 64-bit Virtual Memory Translation Descriptor */
struct PageTableEntry {
    uint64_t physical_frame : 40; /* 40-bit physical page frame address */
    uint16_t reserved       : 11; /* Architecture-reserved bits          */
    uint8_t  cache_disable  : 1;  /* Disable L1/L2 hardware caching      */
    uint8_t  write_through  : 1;  /* Write-through vs write-back policy  */
    uint8_t  user_accessible: 1;  /* Ring 0 kernel vs Ring 3 user mode   */
    uint8_t  read_write     : 1;  /* 0 = Read-only, 1 = Read/Write       */
    uint8_t  present        : 1;  /* Page residency flag                 */
};
#+END_SRC

*Analytical Questions:*
1. What occurs at the hardware level when a thread executes a *write* instruction to an address mapped by this entry if ~present == 1~ but ~read_write == 0~?
2. If page size is $P = 4\text{ KiB} = 2^{12}\text{ bytes}$, what is the maximum physical memory addressable by this descriptor?

\begin{equation}
\text{Max Physical Address} = 2^{(\text{frame bits} + \text{offset bits})}
\end{equation}

| Flag            | Value | Architectural State                         |
|-----------------+-------+---------------------------------------------|
| ~present~         |     1 | Page resident in physical DRAM              |
| ~read_write~    |     0 | Page protected as *read-only*                 |
| ~user_accessible~ |     0 | Accessible only in supervisor mode (Ring 0) |

*** Back :noexport:
*1. Hardware & Kernel Exception Sequence:*
- The CPU Memory Management Unit (MMU) checks page privileges during virtual-to-physical address translation.
- Detecting a store attempt against a descriptor with ~read_write == 0~, the MMU raises a *#PF (Page Fault Exception)* (Vector 14).
- The CPU pushes an error code onto the kernel interrupt stack:
  - Bit 0 (~P~ flag) = 1 (fault caused by page protection violation, *not* a missing page).
  - Bit 1 (~W/R~ flag) = 1 (access was a write).
- Control vectors to the OS interrupt handler, which terminates the violating process with ~SIGSEGV~ or invokes *Copy-On-Write (COW)* logic.

*2. Address Space Mathematical Proof:*
Since the descriptor dedicates 40 bits to ~physical_frame~ and the offset within a 4 KiB page occupies $\log_2(4096) = 12\text{ bits}$:

\begin{align}
\text{Total Address Bits} &= 40\text{ (frame)} + 12\text{ (offset)} = 52\text{ bits} \\
\text{Max Addressable Space} &= 2^{52}\text{ bytes} = 4\text{ PiB (Pebibytes)}
\end{align}

*3. Architectural Topology & Memory Diagram:*
[[file:./assets/page_table_diagram.png]]

*4. Comparison Summary:*
| Dimension        | Translation Failure (~present == 0~)   | Protection Fault (~read_write == 0~)          |
|------------------+--------------------------------------+---------------------------------------------|
| *Exception*        | #PF (Missing entry)                  | #PF (Permission violation)                  |
| *Error Code Bit 0* | 0 (Non-present page)                 | 1 (Protection check failed)                 |
| *Resolution*       | Demand paging from swap/storage      | COW fork replication or ~SIGSEGV~ termination |
```

### Recipe B: Code Analysis Card
```org
** Atomic Compare-And-Swap (CAS) Semantics :lock_free:
:PROPERTIES:
:ANKI_NOTE_TYPE: Basic
:END:

*** Front :noexport:
Analyze the following atomic operation:
#+BEGIN_SRC c
bool atomic_compare_and_swap(uint64_t *ptr, uint64_t expected, uint64_t desired);
#+END_SRC

What condition determines whether the memory update succeeds, and what does the function return?

*** Back :noexport:
*Semantics:*
- If ~*ptr == expected~: writes ~desired~ to ~*ptr~ and returns ~true~ (success).
- If ~*ptr != expected~: leaves ~*ptr~ unchanged and returns ~false~ (failure).

The check and update execute atomically as an indivisible hardware transaction.
```

### Recipe C: Mathematical / Proof Card
```org
** Red-Black Tree Height Bound :complexity:
:PROPERTIES:
:ANKI_NOTE_TYPE: Basic
:END:

*** Front :noexport:
What is the maximum height of a balanced Red-Black Tree containing $n$ internal nodes?

*** Back :noexport:
*Height Bound:*
$$h \le 2 \log_2(n + 1)$$

*Proof Intuition:*
1. Every path from root to leaf has the same black height ($bh$).
2. No two red nodes are adjacent, so red nodes comprise at most half of any path.
3. Therefore, the longest path is at most twice the shortest path: $h \le 2 \cdot bh \le 2 \log_2(n + 1)$.
```

## 5. How to Sync into Anki

Once the `.org` file is generated:

1. Ensure Anki is running with AnkiConnect (`http://127.0.0.1:8765`).
2. In Emacs:
   - **Sync single card under point:** `M-x org-anki-sync-entry` (`C-c a s` or `C-c n`).
   - **Sync all cards in buffer:** `M-x org-anki-sync-all` (`C-c a a` or `C-c s n`).
   - **Re-push existing cards:** `M-x org-anki-update-all` (`C-c a u`).
3. `org-anki` creates notes in the deck specified by `#+ANKI_DECK:` and stamps `:ANKI_NOTE_ID:` into each card's `:PROPERTIES:` drawer.
